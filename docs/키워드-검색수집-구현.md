# 키워드 발굴: 실제 검색 연결 첫 구현

2026-11-14 KST. 사용자 승인: 시뮬레이션 뒤 실제 데이터의 6단계 연결을 우선 구현하고, 검색량 등 세부조건은 뒤에 설정한다. 이 작업은 고객 실습 로드맵의 키워드 발굴·DB 기능 선행 구현이며, 기술 주 단계 A-02는 계속 진행 중이다.

## 이번 코드

- 기존 React/Python 중앙 앱에 검색 입력, 네이버·구글별 결과, 저장 기록, 워드프레스 HTML 신호 확인을 추가했다. 별도 Sites의 정적 시뮬레이션은 수정하지 않았다.
- `ZERO_SERPAPI_KEY`가 서버에 있으면 선택적 SerpApi 어댑터 활성화. 이는 초기 검증용 연결 코드이며 계정 가입·유료 계약·운영 제공자 영구 확정은 아니다. 키는 환경변수로만 받고 화면/일반 백업/저장 기록/오류에 반환하지 않는다.
- 요청당 Naver `nexearch` page=1 / Google ko·kr·desktop start=0을 각 한 번만 요청. 페이지 추가 탐색·자동 재시도 없음. 서버당 한 작업만 동시 실행. Render 기존 workers=1/instance=1 기준이다. 여러 프로세스의 통합 사용량 제한은 미구현.
- 응답의 엔진·원래 검색어·페이지를 검사하고 인식하는 결과 영역만 추출한다. 네이버 블로그와 광고 영역은 제외. 영역 내 번호는 전체 통합 순위로 표시하지 않는다.
- 양쪽 결과 수신과 대상 유형 발견/최종 선별을 구분한다. 한쪽 실패는 `incomplete`, CMS 미확인이나 누락된 영역은 `unknown`. 부재로 판정하지 않는다. 빈 목록도 부재 증명이 아니다.
- 티스토리는 hostname으로 판별. 독립 도메인은 저장된 결과에 한해 명시적 읽기 전용 점검으로 WordPress generator/wp-content/wp-includes HTML 신호를 찾는다. 공개 DNS 검증과 고정 IP HTTPS, 인증/프록시/리다이렉트 없음, 시간/크기 제한. 신호가 없어도 비워드프레스로 확정하지 않는다. HTTP 결과는 자동 HTTPS 변경하지 않는다.
- 기록은 기존 중앙 DB의 별도 `keyword_search_runs` 테이블에 저장. 기존 workspace/.state/초안737·738/백업 호환은 보존. 요청 전 pending 저장으로 중단된 요청을 성공으로 오인하지 않는다. 재실행은 새 기록이며 기존 기록을 덮어쓰지 않는다. 화면은 최근 30개, DB 전체 보존. 이 검색 기록은 기존 v1/v2 JSON에 포함되지 않으므로 운영 DB 백업이 별도 필요하다.
- 로그인/Origin/CSRF로 요청과 점검을 보호한다. 검색량은 미측정이며 원본 글 작성/PBN/백링크/RSS 수집/후보 자동 선별·승격/월간 예약 실행은 아직 아니다.

## 실제 검증 한계와 다음 순서

API 키가 없어 네이버·구글 **실제 API 요청은 실행하지 않았다**. 공급자 응답 모의 테스트가 실시간 검색 성공 증거는 아니다. 한국·비로그인·데스크톱 기준도 개인 화면과 동일한 순위를 보장하지 않는다. API가 지원하지 않는 블록/새 스키마는 별도 검증 필요.

1. SerpApi 무료 계정의 서버 비밀 키 설정. 채팅/소스에 붙이지 않는다. https://serpapi.com/pricing 에서 확인한 무료 플랜 월250검색(2026-11-14 확인). 한 키워드 양쪽 조회는 최대2검색을 사용하므로 대량 실행 전에 할당량 확인. 유료 가입은 하지 않았다.
2. `카카오택시 분실물 조회` 실제 양쪽 결과 수집, 화면과 비교. `namtaegi.com`/`ek5524.tistory.com`는 이전 확인 사례이지 다음 실시간 결과를 보장하는 고정 fixture가 아니다. 코드에 해당 도메인 하드코딩 없음.
3. 인식 영역의 실제 데이터 형식과 누락을 보정한 뒤 블로그별 RSS 수집/후보 추출을 연결. 다른 검색 API를 선택해도 어댑터를 교체하고 DB/UI 구조는 유지 가능.
4. 최종 후보의 양쪽 검색 검토 → 사용자 선택 → 별도 키워드 DB 축적/이력/통합 관리 전달. 세부 검색량 임계값은 사용자 협의 후 설정. 아직 최종 6단계 실동작 완료가 아니다.
