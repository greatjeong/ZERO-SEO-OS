# Windows 연결 서버 실행창 종료 대응

2026-11-13. A-03 실행 도구 개선 및 A-04 검증 준비. 기술 주 단계는 A-02 진행 중 유지.

사용자가 A-1 https://a.webcreatorlabs.com 연결·테스트 초안 저장을 승인했으나 로컬 연결 서버 창이 입력 후 닫혔다고 보고했다. 실제 오류는 아직 확인하지 못했다. Python 미설치·버전, server.py 문법·인코딩, 포트 충돌 등 원인을 확정하지 않는다.

Start-Connector.ps1은 인증정보 입력 전에 Python 3.11 이상을 확인하고 python 실행 불가 시 py -3를 시도한다. 서버 파일 존재와 UTF-8 문법을 확인한 뒤 실행하며 비정상 종료를 표시한다. 종료·실패 후 환경변수를 복원하고 사용자 Enter 입력까지 창을 유지한다. Start-Connector.cmd는 동일 폴더의 스크립트를 -NoExit로 호출해 PowerShell 구문 오류나 실행 정책 차단도 창에 남긴다. 실행 정책은 변경하거나 우회하지 않는다. 인증정보 저장·로그 기록, 기존 .state 변경은 추가하지 않았다.

사용 방법: 기존 backend 폴더에 두 실행 파일만 교체·추가하고 Start-Connector.cmd를 더블클릭한다. 정상 시작 후 창은 그대로 유지하고 대시보드에서 연결 확인을 누른다. 오류가 나오면 인증정보를 가린 오류 부분만 확인한다.

검증: git diff 공백 검사 및 Python preflight 대상 UTF-8 문법 확인. 이 개발 환경에는 PowerShell/Windows가 없어 실제 Windows 실행 검증은 미완료다. 사용자의 PC 오류 확인이 다음 작업이며 이번 수정만으로 연결 성공이나 초안 저장 완료로 표시하지 않는다.

## PowerShell 실행 정책 차단 확인 및 대체 실행

사용자 오류에서 UnauthorizedAccess / Execution_Policies 차단이 확인됐다. 정책 변경이나 Bypass를 사용하지 않는다. Start-Connector.cmd를 Python 직접 실행 방식으로 교체했다. 같은 폴더의 start_connector.py가 getpass로 비밀번호를 숨겨 입력받고, 복사한 자식 프로세스 환경에만 넣어 기존 server.py를 실행한다. PS1은 이 경로에서 사용하지 않는다. 실행 종료 후 CMD pause로 오류 화면을 유지한다. 기존 데이터 및 .state는 건드리지 않는다. Python 구문 검사 통과, Windows 실제 실행은 사용자 PC 확인 대기다.

## 대시보드 5173 연결 거부

사용자 화면에서 http://127.0.0.1:5173/ ERR_CONNECTION_REFUSED 확인. 연결 서버 8765 정상 실행 출력과는 별개다. 화면 서버 종료·미실행 또는 다른 로컬 접속 방해 가능성을 실행 로그 없이 확정하지 않는다. 프로젝트 루트의 Start-Dashboard.cmd를 추가했다. frontend 폴더와 npm 및 Vite 설치를 확인하고 기존 npm run dev를 실행하며 Vite 준비 후 브라우저를 연다. 종료 시 오류를 볼 수 있게 pause한다. 기존 프로세스를 종료하거나 5173 포트를 자동 탈취하지 않는다. 엄격한 고정 포트 설정을 유지한다. 기존 데이터·인증정보·.state는 변경하지 않는다. Windows 실행 및 종료 원인은 사용자 PC의 실행 창 확인 대기다. A-02 로컬 화면 실행 지원 작업이며 A-04 실사이트 인증·초안 검증은 여전히 미완료다.

## 새 앱 비밀번호도 401 — 독립 읽기 전용 진단

사용자가 새 응용 프로그램 비밀번호로 재실행한 뒤에도 rest_not_logged_in 401을 보고했다. 사이트 건강에는 인증 헤더 경고가 없다고 보고했으며, 이것만으로 외부 요청 헤더 전달을 정상으로 확정하지 않는다. 보안 설정 변경·플러그인 해제·비밀번호 재발급을 반복하지 않는다.

Check-WordPress.cmd + check_wordpress.py를 추가했다. 승인된 a.webcreatorlabs.com HTTPS 주소에만 표준 urllib 클라이언트로 GET한다. 공개 REST 발견 정보, 익명 사용자 조회, 인증된 view/edit 사용자 조회를 독립 검사한다. 프록시 환경변수와 리다이렉트를 사용하지 않으며 응답 본문·인증 헤더·비밀번호는 출력하지 않는다. 입력은 getpass로 숨기고 파일에 저장하지 않는다. 앱 비밀번호 입력 형식이 WordPress 기본 24자 형식과 다르면 인증정보를 전송하지 않고 중단한다. 결과는 HTTP 상태·제한된 오류 코드·인증 여부·사용자명 일치·글 작성 권한만 표시한다. 이것은 원인 분리를 위한 진단이며 헤더 차단 여부를 단독 확정하지 않는다.

관련 모의 테스트 3개를 포함해 서버 테스트 40개 통과. 실제 외부 인증 결과는 사용자의 PC 실행 대기다. 사용자명·비밀번호 입력은 새 진단 창에서 한 번 필요하며 기존 대시보드와 연결 서버를 종료할 필요는 없다. A-03/A-04 연결 검증 범위이고 전체 단계 완료를 의미하지 않는다.

## 진단 입력 형식 실패 반복 — 마스킹 입력창

사용자가 두 번 연속 INPUT_PASSWORD_SHAPE_EXPECTED=False를 보고했다. 인증정보는 이 진단에서 전송되지 않았으며, 이를 WP 인증 실패나 헤더 차단의 증거로 해석하지 않는다. 콘솔 붙여넣기 문제 또는 잘못된 입력값 가능성을 아직 구분하지 못했다.

check_wordpress.py의 getpass 입력을 tkinter 네이티브 마스킹 창으로 바꿨다. 붙여넣은 문자는 별표로 표시하고 공백 제외 글자 수만 표시한다. 24자 영문·숫자 조건을 충족해야 Continue로 진행하며 형식이 다르면 창에서 다시 수정할 수 있다. 값·클립보드·원문을 출력·파일 저장하지 않는다. Tk 창이 열리지 않거나 취소하면 인증정보 전송 전에 종료한다. 고정된 승인 사이트와 읽기 전용 GET 요청은 유지한다. 입력 취소와 유효 입력 처리 모의 테스트 추가, 서버 테스트 총 42개 통과. Windows 실제 입력창은 사용자 PC 검증 대기다. 사용자는 check_wordpress.py 한 파일만 교체하고 기존 Check-WordPress.cmd를 실행하면 된다.

## 사용자 PC 독립 인증 성공 및 실행 서버 입력 통합

마스킹 창 적용 후 사용자가 아래 결과를 제공했다: 공개 REST HTTP 200, 앱 비밀번호 지원 True, 입력 형식 True, 익명 조회 401, AUTH_VIEW/EDIT 모두 HTTP 200 AUTHENTICATED=True, USERNAME_MATCHES_CONNECTOR=True, EDIT_POSTS=True. 앱 비밀번호를 이용한 사용자 인증과 글 작성 capability가 사용자 PC의 독립 진단에서 확인됐다. 실제 글 저장 성공은 아직 아니다. 보안 설정 변경 없이 인증이 성공했으며 기존 콘솔 입력 전달 문제 가능성이 커졌다. 서버 클라이언트 차이 등의 다른 원인까지 확정 배제하지 않는다.

start_connector.py에도 check_wordpress.read_password의 동일 마스킹 창을 적용했다. 갱신된 check_wordpress.py가 같은 backend 폴더에 있어야 한다. 이 import는 진단 요청을 실행하지 않고 입력창 함수만 재사용한다. A1/A2 각각 창에서 검증된 입력을 받아 자식 서버 환경에만 전달한다. 진단에서 성공했던 비밀번호를 별도 저장하지 않으므로 서버 재시작 때 한 번 입력해야 한다. 취소 시 서버 실행을 중단한다. 비밀번호가 부모 환경·출력에 남지 않고 자식 환경에 전달되는지, 취소 시 실행되지 않는지 테스트 추가. 서버 테스트 총 44개 통과. 다음은 사용자가 실행 서버를 재시작한 뒤 실제 대시보드에서 인증·권한 확인, 이어 승인된 테스트 초안 저장·재조회다. 기존 .state와 과거 초안 기록을 유지한다.

## 마스킹 실행 서버도 401 — 진단과 조회 캐시 동작 비교

사용자 PC 독립 urllib 진단에서 AUTH_VIEW/EDIT 200과 글 작성 capability가 확인됐으나 마스킹 입력으로 재시작한 대시보드 경로는 여전히 rest_not_logged_in 401을 보고했다. 입력 문제만으로 원인을 확정했던 해석을 철회하며 비밀번호 재발급·보안 해제를 반복하지 않는다.

실제 코드 비교에서 성공한 진단은 GET마다 비밀이 아닌 임의 쿼리와 Cache-Control:no-cache를 사용하지만 기존 server.py는 고정 주소와 캐시 지시 없음이 확인됐다. server.py v0.2.4는 GET에만 매번 다른 _zero_check 식별자를 추가하고 요청 헤더에 no-cache,no-store 및 Pragma:no-cache를 사용한다. 이 변경이 실제 캐시 계층을 보장 우회한다거나 401 원인이 캐시였다고 확정하지 않는다. 아직 알려진 나머지 차이는 urllib와 DNS 고정 http.client 전송 방식, User-Agent 등이다.

POST 주소·횟수·초안 정책·재조회·중복 방지 SQLite·TLS 호스트 검증·DNS 공개 IP 고정·리다이렉트 차단을 유지했다. 사용자 환경의 인증정보·.state는 변경하지 않는다. 서버 시작 출력에 v0.2.4와 fresh authentication requests를 표시해 파일 적용 확인을 돕는다. 조회 URL 신선도와 인증정보 URL 미포함, POST 주소 불변·단일 시도 회귀 테스트 추가. 서버 테스트 46개와 Python 컴파일 통과. 실제 사이트는 이 작업 환경에서 접속 불가하므로 사용자 PC에서 v0.2.4 실행 출력과 대시보드 인증 결과 확인 대기다. 다음은 인증 성공 후 기존 승인 범위의 초안 저장·재조회다. 기술 주 단계 A-02 진행 중을 유지한다.

## v0.2.4 실제 실패 후 진단 요청 방식 정렬

사용자 스크린샷에서 실제 실행 서버 v0.2.4와 대시보드의 HTTP401 rest_not_logged_in이 함께 확인됐다. 따라서 조회 캐시 방지 변경만으로 해결되지 않았고 원인을 캐시라고 확정하지 않는다.

v0.2.5에서 성공한 진단과 동일한 urllib 요청 구성(환경 프록시 미사용, 리다이렉트 차단, 읽기 요청 User-Agent)을 사용하도록 서버를 정렬했다. 연결은 여전히 검증된 공개 IP에 고정한다. 이전 수동 TLS connect를 표준 HTTPSConnection 기본 인증서·호스트 검증과 표준 연결 절차로 교체하고 소켓 생성 대상만 검증된 IP로 고정했다. urllib handler는 이 연결을 사용하며 다른 호스트로 재시도하거나 인증정보를 전달하지 않는다. GET의 신선한 쿼리·캐시 지시를 유지한다. POST는 여전히 같은 URL·한 번 요청이며 초안 저장 후 재조회, SQLite intent·중복 방지, 불확실 결과 재시도 차단을 유지한다. 서버·외부 오류에 인증정보 원문을 노출하지 않는다.

48개 서버 테스트 통과: 기존 권한·초안·저장본 회귀, 표준 TLS 호스트 및 인증서 검증 유지, 공개 IP 소켓 고정, 리다이렉트 시 인증정보 미전달·재요청 없음 포함. Python 컴파일·git diff 검사 통과. 성공한 클라이언트와의 차이를 좁힌 수정이며 실제 사이트 성공 또는 근본 원인 확정은 아니다. 현재 Work에서는 사이트 접근 불가하므로 사용자 PC의 v0.2.5 실행과 대시보드 결과 확인 대기다. 사용자에게 server.py 한 파일만 교체하도록 제공하며 기존 데이터·.state·비밀번호를 바꾸지 않는다. A-02 진행 중 유지, A-03/A-04 안정화 범위다.
