# 키워드 6단계 연결 구현 — 운영 검증 대기

2026-11-14 KST. 사용자 요청: 나머지를 6단계까지 개발하고 Render·SerpApi 준비 후 실제 테스트를 한 번에 진행한다. 이번에는 외부 API 호출·실제 RSS 재시도·WP 변경·카드 등록·유료 자원 생성 없이 코드/내부 검증만 수행했다. 기술 주 단계 A-02는 여전히 진행 중이며, 고객 실습 로드맵의 키워드 발굴·DB 기능을 선행 구현한 것이다.

## 단계별 연결

| 단계 | 구현된 사용자 동작 | 아직 다른 범위인 것 |
|---|---|---|
| 1 시작점 | 키워드 검색 입력 또는 블로그 주소 직접 입력 | 최종 레이아웃 확정 아님 |
| 2 첫 페이지 확인 | 기존 dual-engine API/기록/유형 확인 → 확인된 블로그의 RSS 수집 버튼 | 실제 공급자 결과 일치·누락 검사 필요 |
| 3 후보 추출 | RSS 제목/분류/원문/피드/시작 검색 근거 유지 → 검색용 핵심어 편집·선택 → 검토 대기 | 제목을 자동으로 의미 분석하는 NLP는 아님 |
| 4 선별 | 후보별 네이버·구글 재검색 또는 일치하는 저장 검색 기록 연결 → 유형 근거 확인 → 이유와 함께 수동 선택/제외 | 검색량 미측정, 임계값 미설정. 자동 수치 필터 없음 |
| 5 DB·재검증 | 전역 재사용 키워드 원본, 출처 통합, 상태/변경 이력, 다음 달 검사일, 재검증, 전체 내보내기 | 운영 스케줄러 연결/실제 PG는 배포 후 |
| 6 원본 글 연결 | 활성·양쪽 확인 완료 키워드 → 서버에 저장된 A-1/A-2 URL의 통합 관리 작성 준비 목록 | AI 글 생성·WP 글 저장/발행·PBN/백링크는 별도 후속 기능 |

## 데이터·상태 규칙

- 새 `keyword_bank`는 검토 대기 후보와 활성/제외 자산을 구분한다. 제목에서 다듬은 검색어와 RSS 원래 제목·출처를 함께 보존. NFKC/casefold/공백으로 키를 만들고 같은 검색어의 출처만 합친다. 수집 반복만으로 제외 상태를 복원하지 않는다.
- RSS → 검토 대기에는 네트워크 조건 필터를 적용하지 않는다. 활성 선택은 최신 근거에서 **양쪽 검색 수신**과 최소 한쪽의 티스토리/WP 판별 근거가 필요하다. 양쪽 모두 대상 유형 노출 필수인지/검색량 등 자세한 조건은 아직 미정이며 수동 검토 모드다. ‘미확인’은 ‘없음’이 아니다.
- 같은 키워드 검색만 연결하며 다른 검색어/더 오래된 결과의 덮어쓰기 거부. revision 충돌은409로 현재 자료 유지. 활성화/제외는 이유 필수, 원본과 이벤트 이력을 지우지 않는다.
- 양쪽 수신 성공 시 최근 확인 시점 갱신. 활성의 대상 유형이 유지되면 다음 달 같은 날짜(말일 보정)로 재검증 예정일 갱신. 실패/유형 미확인은 활성 원본을 보존하고 검토 필요 및 다음 날 재확인 표시. 조회 실패 시 이전 성공일·정기 검사일 보존.
- 현재 공급자 파서는 인식 가능한 영역만 다루므로 ‘없음’을 확정할 수 없다. 따라서 **자동 부재 판정·자동 제외는 구현 완료라고 부르지 않는다.** 근거 미확인은 검토 대상으로 남기며 양쪽 수신 후 사용자가 이유를 기록해 활성 제외할 수 있다. 완전한 부재 판정 기준은 실제 결과와 세부조건 협의 후 연결.
- 작성 준비는 키워드ID+canonical URL로 중복 방지. A-1/A-2가 같은 URL이면 같은 준비 목록, 서로 다른 URL에는 재사용 가능. 원본 DB/출처/이력은 유지. 나중에 제외·검증 미완료 또는 대상 슬롯 URL 변경이 생기면 준비 목록도 실행 적격이 아님으로 표시한다. 실제 글 작성 작업은 실행하지 않는다.
- DB 신규 테이블 `keyword_bank`, `keyword_bank_events`, `original_article_preparations`만 추가. 원래 workspace/737·738/.state는 그대로 유지. 전체 별도 JSON export 제공(아직 import 복원 도구 아님). 기존 v1/v2 workspace JSON은 호환 유지하며 새 테이블을 포함하지 않는다. 운영 DB 백업이 별도로 필요하다.
- bank 조회는100개씩 페이지 처리, 내보내기는 전체 DB/출처/이력/작성 준비를 포함. 소유자 세션과 Origin/CSRF 사용. UI에서 원문 URL/외부 내용을 실행 코드로 삽입하지 않음.

## 월간 실행 준비

`python backend/recheck_keywords.py --limit 5`는 같은 DATABASE_URL과 서버 비밀 환경을 사용하며, 기한이 지난 활성 키워드를 최대5개 재검증한다. 월간 예정일을 가진 레코드를 일일 스케줄에서 처리하는 방식. 현재 스케줄 등록이나 배포는 하지 않았다. 검색 실패는 재확인일 전 반복하지 않는다. 각 키워드 양쪽 API 최대2회로 예산을 제한하지만 다중 프로세스 전역 네트워크 호출 중복 방지는 아직 아니므로 초기 단일 실행만 구성한다. 운영 규모가 커지면 작업 claim/분산 잠금·할당량 정책을 추가 검증한다. 공급자 키가 없으면 실행 없이 종료한다.

워드프레스 유형은 수동 페이지 점검 버튼으로 근거를 추가할 수 있다. 주기 검사에서 독립 도메인 유형이 미확인되면 자동 탈락시키지 않는다. 전체 CMS 자동 판별/공급자 블록 보강은 실제 운영 테스트 결과에 따라 보완한다.

## 내부 검증

- 서버119개(이번 신규13개)·화면27개(신규4개) 통과. TypeScript/Vite 빌드, Python compile, diff 검사 통과.
- 후보 staging 트랜잭션 전부 롤백, 정규화 중복, 제외 상태 보존, 다른 검색어/미완료 근거/오래된 revision 거부, 월말/연말 예정일, 실패의 활성 원본·성공일 보존, 원본 글 중복/여러 사이트 재사용, 사이트 변경/제외 후 적격 차단, 재시작·내보내기·이력, 인증/CSRF 검증.
- 6단계 API 흐름은 공급자/RSS를 모의해 테스트. 실제 SERP/RSS/Render/PG/E2E 성공 증거가 아니다. 기존RSS 실수집 연결 실패 기록도 그대로 유지.
- 사용자 요청에 따라 실제 통합 테스트는 Render·SerpApi 설정 후 한 번에 진행한다. 서비스 가입/카드/키를 지금 다시 요청하지 않는다. 별도 정적 Sites 시뮬레이션은 변경하지 않았다.

## 운영 준비 후 한 번에 검증할 순서

1. Render 앱/PG 배포, 서비스 소유자 로그인, `ZERO_SERPAPI_KEY` 서버 비밀 설정(채팅/소스 금지), 앱 HTTPS 주소 확인.
2. 기준키워드 `카카오택시 분실물 조회` → 네이버·구글 모두 첫 페이지 확인. 화면과 공급자 결과 비교, 광고·네이버 블로그·유형 미확인·누락 상태 확인.
3. 발견한 WP/티스토리의 RSS 버튼 → 실제 피드 글 목록·제목·분류·원문 및 시작 검색 근거 확인. 불가한 사이트는 미완료 유지.
4. 후보를 핵심어로 편집·검토 대기로 보내기 → 후보마다 양쪽 검색 확인 → 필요한 WP 유형 점검 → 수동 이유와 함께 선택. 실패/미확인으로 활성 승격되지 않는지 검사.
5. 새로고침/재로그인/서버 재시작 후 출처·키워드·상태 유지, 중복 후보 통합, 전체 export 확인. 재검증 성공/실패/제외 이력 확인.
6. 서버에 저장한 실제 대상 사이트로 작성 준비 연결. 동일 사이트 중복 방지, 다른 사이트 재사용, 원본 DB 보존 확인. **추가 WordPress 글은 만들지 않는다.**
7. 배포 후 별도 운영 스케줄 등록·동일 DB/키 확인, 월간 예정일 및 실패 재확인 동작 검사. 실제로 한 달이 지났다고 주장하지 않고 시험 시각/시험 DB임을 명시한다.
