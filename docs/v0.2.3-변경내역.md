# v0.2.3 연결·데이터 보관 안정화

기준일: 2026-11-13 (한국 시간). 기술 주 단계 A-02 진행 중 유지. 이번 요청으로 승인된 A-03/A-04 연결 안정화 선행 작업을 포함한다. 전체 사업 단계 완료를 의미하지 않는다.

## 최신 소스 분석

GitHub main의 `988084d`에서 시작했다. v0.2.2 커밋이 원격에 존재함을 확인했다. 저장소에는 FastAPI 서버 또는 중복 실행 서버가 없으며 `backend/server.py`의 표준 라이브러리 HTTP 서버 하나가 실행 진입점이다. 사용자의 PC에서 실행한 별도 FastAPI 파일은 이 저장소에서 확인할 수 없다. 임의 삭제하거나 프레임워크를 변경하지 않았다.

기존 소스는 UTF-8 해독·Python 컴파일 및 서버 테스트 25개를 통과했다. 보고된 문법·인코딩 오류는 현재 원격 소스에서 재현되지 않았다. UI의 실제 인증 요청, 권한 확인, 초안 저장 후 재조회, SQLite 중복 생성 차단이 이미 구현되어 있어 유지했다. 진단 도구의 별도 HTTP 구현은 같은 커넥터 함수 호출로 통합하고 특정 실제 도메인의 하드코딩을 제거했다.

## 변경 사항

- 사이트 등록은 localStorage 쓰기에 성공한 뒤에만 등록 완료 표시. 읽기 시 자동 덮어쓰기를 제거했다.
- 키워드·작업은 실제 변경 시 저장하며 저장 실패를 표시한다. 시작 시 손상된 기존 저장 원문도 자동 초기화하지 않는다.
- JSON v2는 사이트 이름·HTTPS 주소, A-1/A-2 키워드, 작업을 포함한다. v1 복원도 유지하며 v1은 사이트 설정을 건드리지 않는다. v2 복원 시 사이트 컴포넌트를 새로 열어 이전 연결 성공 상태가 남지 않는다.
- 서버 보관 버튼은 `backend/.state/workspace.sqlite3`에 트랜잭션으로 전체 저장본을 추가한다. 과거 저장본을 갱신하거나 삭제하는 API는 없다. 조회는 최근 100개를 표시하며 데이터 자체는 모두 유지한다.
- 서버 저장본 복원은 JSON 파일 복원과 동일한 검사·확인 절차를 사용한다. 자동 복원·자동 동기화는 하지 않는다. 현재 브라우저 데이터를 먼저 JSON으로 보관한 뒤 교체해야 한다.
- 저장 데이터는 허용된 필드만 수용한다. 사이트 인증정보, 예상하지 않은 작업 필드, 중복 작업 ID를 거부한다. 인증정보는 서버 프로세스 환경변수만 사용하며 브라우저·Git·서버 저장본에 넣지 않는다.
- Host·Origin 확인, HTTPS, 공개 IP 검사, DNS 검증 주소에 TLS 연결 고정, 리다이렉트 거부를 유지했다. 인코딩된 호스트 거부, 요청 본문 읽기 시간 제한, chunked 본문 거부를 보강했다.
- 인증 성공은 일치하는 사이트·주소·검증 결과·유효한 확인 시각이 있어야 표시한다. 테스트 글은 `status=draft`로만 요청하고 별도 GET으로 같은 ID의 초안 상태를 재확인해야 저장 성공을 표시한다. 공개 발행 API는 추가하지 않았다.

## 실행과 데이터 보존

기존 실행 방식 유지: 화면은 frontend Vite, 연결 서버는 backend/Start-Connector.ps1 또는 backend/server.py. 별도 FastAPI 서버를 동시에 실행할 필요가 없다. 커넥터는 로컬 127.0.0.1:8765, 화면은 127.0.0.1:5173만 허용한다. 비개발자는 기존 실행 경로를 그대로 사용하고 새 백업·보관 버튼을 이용하면 된다.

업데이트 시 기존 `backend/.state`와 브라우저 프로필을 유지한다. 특히 `test-drafts.sqlite3`는 초안 중복 방지 기록이다. 새 workspace DB는 이 파일과 별개로 생성되며 기존 파일을 변경하지 않는다. 서버 보관은 버튼을 눌렀을 때만 실행된다. 서버 DB는 이 PC의 로컬 저장이며 다중 사용자 SaaS DB가 아니다. 저장본은 평문이므로 장치 접근 권한을 관리해야 한다. DB는 Git에서 제외된다.

## 검증

- Python UTF-8 소스 컴파일 및 서버 unittest 37개 통과 (기존 경로 회귀 포함).
- React 화면 로직 테스트 7개: 사이트별 분리, 대기열 취소·재등록, 재마운트 보존, 인증 응답 불일치 거부, 저장 실패 표시, v1/v2 복원, 인증정보 필드 거부, 초안 확인 단계, 손상 원문 보존.
- TypeScript/Vite 프로덕션 빌드·oxlint 통과.
- 실제 HTTP 핸들러를 통한 SQLite 저장·재조회 및 이전 저장본 보존 검증.
- Playwright E2E 시나리오 2개를 추가했으나 현재 실행 환경에서 Chromium 시작이 OS socket 권한 오류로 차단되어 실행 완료하지 못했다. 화면 로직 테스트는 DOM 환경에서 수행했으며 실제 브라우저 E2E 통과로 표현하지 않는다.
- 실제 WordPress 요청·글 생성·공개 발행은 이번 작업에서 실행하지 않았다. 기존 문서의 글 ID 737은 과거 기록이며 이번 검증 결과가 아니다.

## 다음 작업과 미확인 사항

1. GitHub 반영 후 사용자의 실제 실행 환경에서 브라우저 E2E와 JSON 파일 다운로드를 확인한다.
2. 사용자가 승인한 실제 사이트에서 인증·권한·테스트 초안 1건의 저장·재조회·재클릭 중복 방지를 검증한다. 사이트별 승인과 서버 인증 설정이 필요하다. A-2는 여전히 실제 검증 미완료다.
3. A-02 메뉴·화면별 흐름과 완료 조건 확정은 별도 남은 작업이다. 전용 WordPress 플러그인·다중 사용자 인증·운영 배포는 구현하지 않았다.
4. 사용자의 PC 원본 브라우저 데이터와 .state는 이 작업 환경에 없으므로 실제 데이터 백업 완료를 주장하지 않는다.

개발자 재검증: backend에서 `python -m unittest discover -s backend`, frontend에서 `npm test`, `npm run build`, `npm run lint`. E2E는 두 로컬 서버 실행 후 `npm run test:e2e`로 실행한다. Chromium 설치가 필요하며 시스템 Chromium을 쓰는 환경은 ZERO_TEST_CHROMIUM으로 실행 파일 경로를 지정할 수 있다. 모든 테스트는 실제 WP 인증정보 없이 실행한다.

## Git 반영 상태

최초 HTTPS push는 GitHub 쓰기 인증 부재(`could not read Username`)로 실패했다. 이후 사용자가 GitHub를 연결하여 원격 main 988084d를 다시 확인했다. 연결된 GitHub API를 통해 검증된 변경 파일로 트리와 커밋을 생성하고 main을 fast-forward하는 방식으로 반영한다. 원격 HEAD와 로컬 파일 트리의 일치는 업로드 후 별도로 확인하며, 확인 결과를 최종 보고에 제공한다. 실제 WordPress 테스트는 계속 승인 대기다.
