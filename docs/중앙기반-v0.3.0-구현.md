# 본인용 중앙 기반 v0.3.0 구현

2026-11-13 · 고정 기준에 따른 App·SaaS 기반 구현. 실제 배포는 아직 아님.

## 실제로 추가한 동작

- 본인 로그인·로그아웃·세션 갱신. WordPress 앱 비밀번호와 별개인 서비스 비밀번호를 사용한다.
- 서버에 사이트 이름·주소, 사이트별 키워드, 작업 기록을 저장한다. 중앙 화면은 브라우저 localStorage를 읽거나 쓰지 않는다.
- 저장은 `변경 사항 서버 저장`을 눌러 실행한다. 저장 확인 전에는 `저장 전 변경 있음`으로 표시한다. 서버 오류·충돌 시 화면 변경을 유지하며 자동 재시도하지 않는다. 저장 전 새로고침·창 닫기는 브라우저 확인을 요청한다.
- 최초 서버 데이터가 없으면 JSON 가져오기 또는 빈 작업 공간 시작을 명시적으로 선택한다. 기존 브라우저 데이터를 자동 초기화하지 않는다.
- 서버 저장은 revision 비교 후 트랜잭션으로 새 저장본을 추가한다. 다른 창에서 먼저 저장했으면 409로 거부하고 데이터를 덮어쓰지 않는다.
- JSON v1/v2 가져오기는 서버 검사·개수 미리보기·사용자 확인 후 적용한다. v1은 서버의 사이트 이름·주소를 유지한다. 예전 저장본을 복원해도 새로운 버전으로 추가하고 과거 저장본은 유지한다.
- 키워드 등록·사이트 분리·작업 등록·취소·재등록을 중앙 화면에서 사용한다. 등록된 작업은 실행하지 않는다.

## 유지된 것과 아직 연결하지 않은 것

기존 로컬 index.html/App, server.py v0.2.5, .state 및 사용자 WordPress 글 737/738은 변경하지 않았다. 소개 홈페이지는 이번 구현 대상이 아니다. 같은 React/Python 저장소에 중앙 화면 central.html과 FastAPI 계층을 추가했다.

이 첫 묶음에는 중앙 WordPress 자격 저장·실제 연결·초안 실행을 넣지 않았다. 중앙 화면에 이를 명시하고 임의로 localhost 연결을 호출하지 않는다. 기존 초안 DB 이관도 아직 수행하지 않았다. 이미 성공한 로컬 연결 코어는 다음 중앙 연결 묶음에서 재사용한다. 고객 등록·다중 사용자·결제·공개 발행·실제 배포는 완료하지 않았다.

## 구체적인 구현 선택

- Python 웹 계층: FastAPI. 기존 로컬 표준 라이브러리 서버를 대체하거나 삭제하지 않고 별도 중앙 진입점을 추가했다.
- 첫 본인용 저장 구현: 전용 중앙 SQLite의 단일 인스턴스·단일 영속 디스크. 기존 PC SQLite를 공유 폴더로 올리거나 .state를 덮어쓰지 않는다. 여러 호스트/인스턴스의 중앙 DB로 사용하는 안은 아니다.
- 서비스 세션: 임의 토큰의 SHA-256 해시를 DB에 저장, 원문 토큰은 HttpOnly·Secure·SameSite=strict·host-only 쿠키로만 전달한다. 세션은 8시간, 로그아웃은 DB에서 폐기한다.
- 비밀번호: 표준 라이브러리 scrypt 해시만 배포 환경변수로 설정한다. n=2^17, r=8, p=1, 임의 16바이트 salt. 기본 비밀번호·회원가입·초기 공개 설정 API는 없다. 해시 설정이 없으면 서버 생성이 실패한다.
- 변경 요청: 정확한 HTTPS Origin과 세션별 CSRF 토큰이 필요하다. 세션·CSRF 값은 응답과 메모리에서만 사용하고 브라우저 저장소에 넣지 않는다.
- 로그인: 클라이언트별 분당 5회·전체 20회 시도 제한을 DB에 기록하고, 동시 scrypt 계산을 최대 2개로 제한한다. 프록시의 클라이언트 IP 신뢰 범위는 실제 호스팅 설정 시 확인해야 한다.
- 일반 JSON 데이터는 평문 DB에 저장한다. 인증·파일 권한·HTTPS와 별개로 데이터 전체 암호화 구현을 주장하지 않는다. WordPress 자격은 이번 DB에 저장하지 않는다.
- schema user_version=1. 알 수 없는 미래 버전 DB는 수정하지 않고 실행을 중단한다.

이 선택은 고정 기준을 바꾼 것이 아니라 본인용 첫 구현이다. 확장 DB·호스팅 제품은 아직 미정이며 고객용 공개 전에 소유권 모델과 운영 저장소를 별도 검증해야 한다. 단순히 회원가입 버튼을 추가해 다중 사용자로 열면 안 된다.

## 검증과 한계

- 기존 테스트를 포함해 backend unittest 67개, 화면 DOM 테스트 15개.
- TypeScript·Vite 두 진입점 빌드, lint, Python 컴파일 검사.
- 두 TestClient 세션과 앱 팩토리 재생성 후 같은 DB 데이터 조회를 검증했다. 실제 PC 두 대·외부 서버·HTTPS 프록시 운영 검증과는 구분한다.
- 인증 없는 모든 데이터 API 거부, CSRF/Origin 거부, Secure cookie, 만료·로그아웃·비밀번호 해시 교체 후 세션 거부, 로그인 시도·계산 동시성 제한을 테스트했다.
- 동시 저장은 한 요청만 성공하고 다른 요청은 409, 실패한 가져오기는 원본 보존, 이전 저장본 조회와 미래 스키마 미수정, 정적 자원 외 DB/소스/.env 미공개를 테스트했다.
- 이 작업에서 실제 WordPress 요청·새 글 생성·기존 글 삭제·사용자 PC 데이터 이관을 하지 않았다. 전체 보안 인증 또는 실제 브라우저 E2E 통과를 주장하지 않는다.

## 배포를 준비할 개발자용 실행 계약

사용자는 지금 새 파일을 내려받거나 PC에 다시 설치할 필요가 없다. 실제 배포 시 운영 환경 설정과 데이터 복사를 작업자가 수행한다.

필수 서버 환경변수:

| 이름 | 값 |
|---|---|
| ZERO_CENTRAL_ORIGIN | 실제 HTTPS 출처, 예: https://서비스주소 (경로·마지막 / 없음) |
| ZERO_CENTRAL_DATA_DIR | 웹 루트 밖의 영속 디스크 절대 경로. 기존 backend/.state 사용 금지 |
| ZERO_OWNER_PASSWORD_HASH | central_auth.py로 만든 scrypt 해시. Git/일반 JSON에 저장 금지 |

저장소 루트 기준 개발자 검증:

```sh
python -m pip install -r backend/requirements-central-dev.txt
python -m unittest discover -s backend -q
npm ci --prefix frontend
npm test --prefix frontend
npm run build --prefix frontend
npm run lint --prefix frontend
```

환경변수를 안전하게 설정한 운영 환경에서 시작할 예시:

```sh
uvicorn central:create_app --factory --app-dir backend --host 127.0.0.1 --port 8000 --workers 1
```

HTTPS 프록시가 해당 프로세스에 연결하도록 구성해야 한다. 이 명령만 실행한다고 공개 HTTPS 서비스가 만들어지지 않는다. 제공자의 포트·프록시·영속 디스크는 배포 시 맞춘다. env 파일은 코드가 자동 로드하지 않으며 호스팅 비밀 설정 기능 또는 프로세스 환경에 설정한다. 중앙 API는 `/api` 경로, 빌드 화면은 `/central.html`, 루트는 중앙 화면으로 이동한다. 운영 데이터 폴더를 정적 파일로 공개하지 않는다.
